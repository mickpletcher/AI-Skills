# Behavioral model-runner setup

PowerShell Refactor evaluation requires eight model comparisons from `evaluations/fixtures/powershell-refactor.json`.

Execution is gated on configured provider access and explicit selection of exact model IDs. No credentials belong in this repository.

For each case, run the original Claude skill and the generated candidate in isolated sessions with identical prompts and model settings. Capture the responses, review `must_preserve` and `forbidden_claims`, and record model IDs, timestamps, commit SHAs, and pass/fail evidence. Capture-only runs do not execute generated scripts. Separately authorized runtime testing requires reviewed synthetic artifacts, temporary workspaces, bounded execution and separate result records; see the [initial runtime assessment](foundation-runtime-2026-10-19.md).

The API runner requirements above are separate from the bounded Codex CLI pilot below. Run-specific evidence, not this setup guide, establishes which model responses were captured.

The optional `tools/run_powershell_behavior.py` runner requires a direct HTTPS endpoint: all redirects are rejected so authentication cannot be forwarded to another endpoint. It does not retry failed requests. An existing output path is refused to preserve prior results. Each completed response is saved through an atomic checkpoint before the next request. Output retains `mode` and `cases` and adds `status` (`running`, `completed`, `partial`, or `error`); failures include the case ID and exception type, without provider error text or credentials. A failed run exits nonzero; keep its partial file and use a different output path for any subsequent run. An abrupt interruption may leave `status: running`, with all previously checkpointed cases intact.

## Foundation text-only pilot

The 2026-10-19 pilot uses [foundation-pilot.json](fixtures/foundation-pilot.json) and a local orchestration script outside the repository. It runs 36 sequential responses through the existing signed-in Codex CLI account, without an API key or changes to the API runner. The requested model is the configured `gpt-6.1-sol`, with medium reasoning; temperature is not exposed by this CLI run and is not assumed. The exact CLI version, requested model, source commit, fixture/instruction hashes, candidate build provenance, timestamps, usage and output hashes are checkpointed with every response. A resolved backend snapshot is not claimed when the runtime does not report one.

Each session uses an empty workspace, read-only sandbox, ephemeral session storage, ignored user configuration and project instruction bytes capped at zero. Per-run flags disable app integrations, plugins, shell tools, shell snapshots and web search. A one-token skill-catalog budget removes unrelated skill descriptions, as confirmed by the canary trace; this diagnostic is recorded rather than treated as a domain failure. Settings apply only to these invocations. No persistent account or host configuration is changed. The [official configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference) and [non-interactive CLI reference](https://learn.chatgpt.com/docs/developer-commands?surface=cli) document these controls.

The orchestration script supplies the common text-only environment guard, the selected instruction condition, and the synthetic scenario prompt. Rubrics and expected outcomes are withheld from the model. Every condition receives identical user input, model settings and requested environment restrictions. Original and candidate source bytes must match the recorded Git commit before calls begin. The fixture and full instruction texts are snapshotted locally before the batch starts. These supplied inputs are not proof of the host's complete effective context.

The capture loop does not retry failures, overwrite existing result manifests, execute generated code, install skills, or promote anything. Runtime failures or observed tool calls stop the batch with a partial checkpoint. Empty outputs and missing completed-turn events invalidate a run. Full outputs and traces remain outside Git pending explicit publication review. Tool availability, natural routing, generated-code execution, broader host coverage and the remaining full-suite scenarios require separate evaluation. Two repetitions are a pilot, not a statistical equivalence claim.

### Context-isolation failure in the first run

The first 36-response batch is context-confounded. Three outputs used profile facts not present in the fixture or selected instruction source. Local prompt rendering retained matching profile context even with the requested zero/one-byte project-document cap and memory injection disabled. The [global instruction chain](https://learn.chatgpt.com/docs/agent-configuration/agents-md) and effective host context must be inspected separately from user configuration. Do not repeat the first harness unchanged or claim that its flags isolate all instructions.

Before further comparison calls, use an authenticated evaluation runtime without unrelated global guidance, memory or skills, and inspect its complete effective request/context. Verify the exact supplied guard, condition and prompt, and fail closed if external profile content remains or the context cannot be audited. A dedicated evaluation identity/profile or an explicitly configured direct model endpoint may be needed. Preserve the existing account configuration, credentials and other chats; do not temporarily replace shared global instructions to make a test pass. Keep the first run's source bytes, outputs and manifest immutable, and record new runtime/settings provenance for the replacement run. Human acceptance and promotion remain blocked.

### Replacement run isolation

The replacement harness uses a separate, process-local `CODEX_HOME` outside Git and an empty workspace. Only the existing login is provisioned into that profile, with the source credential file's ACL. The harness never prints credentials or places them in prompts or manifests. Remove the temporary credential copy after the batch. The shared profile, global instructions and account configuration remain untouched.

The evaluation profile must not contain `config.toml`, `AGENTS.md`, `AGENTS.override.md` or memories. Both memory consumption and generation are disabled. A fixed, snapshotted `model_instructions_file` replaces the CLI's default base instructions. The other text-only restrictions remain enabled. These are client-context controls; no claim is made about access to provider-owned system instructions.

Before the batch and before every comparison call, render the input list with `codex debug prompt-input` using the same profile, working directory, model, sandbox, approval setting and configuration overrides as `codex exec`. The debug command has no `--ignore-user-config` option, so an absent profile configuration is required rather than assuming the commands ignore the same files.

The gate requires the exact selected developer instruction and user prompt once each. Remaining messages must be the reviewed generic CLI infrastructure: an empty skill catalog, permission and collaboration instructions, and environment metadata. Reject extra user guidance/history, unexpected developer guidance or content types, unrelated skill descriptions, known contamination markers, and any change to the normalized infrastructure between conditions. Persist the complete local render and hashes with each capture. Render/input hashes cover UTF-8 text normalized by subprocess text mode; source, fixture and response hashes cover file bytes. A rejected audit stops before inference and preserves the partial manifest.

Eight offline checks exercise clean input acceptance and rejection of unrelated user guidance, unknown developer guidance, skill descriptions, altered task input, response history, changing infrastructure and unexpected content. The previous confounded batch remains immutable. A separate sandbox-network failure before the replacement run produced no completed model response and is retained separately, rather than silently retried into its manifest.

The replacement remains a forced-instruction text-only pilot. Original, candidate and control all use the same new base instructions; its scores cannot be compared causally with the confounded batch. Requested model identity, rather than an unreported backend snapshot, is the reproducible runtime label. Assistant rubric assessment is separate from human acceptance.

### Revision 2 and runtime execution

Fixture revision 2 adds `architect-whitespace-regression` and pins `bool(line.strip())`, Unicode whitespace, universal newlines and the final unterminated line. Preserve historical fixture snapshots and hashes. A complete revision-2 comparison would be 42 responses; the initial runtime phase captured only two repetitions of each architect candidate case. Existing PowerShell/README captures were reused only after hash verification.

Before any runtime command, inspect the proposed source/build/test files, verify capture hashes, require complete extracted files, and use separate temporary projects and environments. Provision trusted dependencies separately. Keep generated package installs offline, suppress unrelated test plugins, apply command timeouts and retain stdout/stderr and exit codes. Compare independent fixture oracles with actual installed entry points; do not rely only on generated tests. Keep raw failures and any repaired copy separate. Local Windows success does not certify generated hosted CI, Linux or human acceptance.

### Fresh tool workflow protocol

The [fresh tool assessment](foundation-tool-workflows-2026-10-19.md) uses separate ephemeral sessions with only the selected candidate, capability contract, task and synthetic repository. Preprovision tools separately, verify a real write/read canary, then enable workspace file/shell operations with network access configured off. Keep expected answers and independent probe snapshots outside the agent workspace. Do not pass previous failures, proposed fixes or assessment criteria to the agent.

Audit exact initial instructions and normalize only expected workspace-path differences when comparing infrastructure, including XML escaping in environment metadata. Retain source/fixture/context/tool/output hashes, intermediate failures and final file hashes. Review source before independent execution. Compare PowerShell public metadata and observable results against a pre-edit baseline with identical analyzer settings; execute the final README's exact documented commands; check architect formatting, lint, tests, CLI oracles and delivered source hashes. Keep human acceptance separate from assistant assessment and do not expand the batch until the requested human review is complete.
