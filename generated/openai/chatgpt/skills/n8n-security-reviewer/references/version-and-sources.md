# Product evidence and version caveats

Official sources checked 2026-11-03. These are point-in-time documentation observations, not the user's installed version, runtime tests, or guarantees. Recheck relevant pages when reviewing. The former `/hosting/...` paths currently redirect to `/deploy/...`; canonical destinations below were retrieved successfully.

- **Export boundary:** [Export/import](https://docs.n8n.io/build/manage-workflows/export-and-import.md) says workflow JSON includes credential references, and imported cURL headers can contain authentication material. Names can reveal information; IDs alone are not secret credentials. Saved exports do not prove production publication.
- **Webhook controls:** [Webhook node](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.webhook) documents separate test/production URLs and several auth modes. CORS and IP restrictions are separate options. Its `Only Run If` evaluation fails open on expression error, so it is unsuitable as the sole security gate. Verify the target version and node schema before using new controls. HTML response iframe wrapping is documented from 1.103.0; this does not prove an arbitrary response is safe.
- **Outbound requests:** [HTTP Request](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.httprequest) documents credential-backed authentication, a TLS-validation bypass option, redirects, proxy configuration, and response-derived pagination URLs. Assess each relevant path, not just the initial URL.
- **SSRF:** [SSRF protection](https://docs.n8n.io/deploy/host-n8n/configure-n8n/security/enable-ssrf-protection.md) documents availability from 2.12.0 and `N8N_SSRF_PROTECTION_ENABLED`. It is an additional layer alongside network restrictions. Hostname allowlists take precedence over IP blocking, so broadly allowed hosts need scrutiny. An explicitly enabled flag is still not evidence that the deployed process loaded it or covers every node/runner.
- **Version/default conflict:** [v2.0 changes](https://docs.n8n.io/changelog/v20-breaking-changes.md) describe blocked Code-node environment access, task runners, and settings permissions as v2 defaults. The [security environment-variable table](https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/use-environment-variables/security.md) currently lists different defaults for some of these, including environment access and permission enforcement. Do not infer defaults from the generic table when version-specific guidance conflicts. Request effective config or matching release/source evidence and report unresolved differences. The v2 guide also distinguishes publishing from the prior activation UI and warns about runner insecure mode.
- **Runner isolation:** [Hardening task runners](https://docs.n8n.io/deploy/host-n8n/configure-n8n/security/harden-task-runners.md) recommends external mode, reduced images, an unprivileged user, constrained writable storage, and host security controls. These require deployment evidence; Code-node existence cannot establish them.
- **Import and runner settings:** [Node variables](https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/use-environment-variables/nodes.md) and [runner variables](https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/use-environment-variables/task-runners.md) distinguish module permissions and runner configuration. The runner documentation places external-mode import settings in launcher `env-override` configuration, not ordinary container variables. It also marks some older runner flags deprecated. Supplied flag values alone therefore cannot establish effective protection or permissions.
- **High-risk nodes:** [Block specific nodes](https://docs.n8n.io/deploy/host-n8n/configure-n8n/security/block-specific-nodes.md) documents `NODES_EXCLUDE` and default blocking for some nodes. Recommend exclusions only after checking compatibility and business needs; never remove exclusions merely to run a review.
- **Execution retention:** [Execution environment variables](https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/use-environment-variables/executions.md) distinguishes success/error/manual/progress storage and pruning. Workflow overrides, old data, backups, and external logs require separate evidence.
- **Redaction gate:** [Redact execution data](https://docs.n8n.io/deploy/host-n8n/configure-n8n/security/redact-execution-data.md) currently limits this feature to Cloud/self-hosted Enterprise. It lists per-workflow support from 2.16.0 and instance enforcement from 2.26.0. Visibility is restricted rather than proof of deletion; privileged reveal and enforcement behavior affect the review. Suggest data minimization, reduced retention, and access limits where the feature is unavailable.
- **RBAC gate:** [Roles and permissions](https://docs.n8n.io/administer/manage-users-and-access/set-permissions-and-roles-rbac.md) currently lists project roles on all Cloud plans and Registered Community/Business/Enterprise self-hosting; custom roles are Enterprise. Do not apply historical “RBAC is entirely Enterprise” assumptions. Check the installed version/plan and actual sharing.
- **Secret-store gate:** [External secret stores](https://docs.n8n.io/administer/manage-credentials/use-external-secret-stores.md) currently lists Enterprise availability. External secret expressions resolve in credential fields, not arbitrary expression fields. Project/global vault access and underlying provider permissions still need least-privilege review. Never ask for vault values.
- **Native audit distinction:** [Run security audits](https://docs.n8n.io/deploy/host-n8n/configure-n8n/security/run-security-audits.md) describes a live CLI/API/node operation with its own reports. This skill does not invoke it or claim equivalence. A user-supplied existing report may be reviewed as evidence with provenance and limits.
