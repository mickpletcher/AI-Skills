# Reviewed copies, not destructive renames

Use report-only unless the user explicitly authorizes file operations. For the helper, explain that it makes renamed **copies** and retains all originals; get approval for that operation and the exact source/output folders and mapping. Permission to rename is not permission to silently duplicate a large collection or delete originals.

Prerequisites: Python 3.10+ standard library, readable regular source files, an existing writable output folder, and a trusted local filesystem with exclusive file creation. No image library, network, installation, or personal test inputs are needed. This helper does not identify photos; use reviewed names from the skill. Stop other writers first. It rejects symlink/junction parents, but is not a security boundary against concurrent folder replacement or hostile filesystem activity; do not execute in that situation.

1. Inventory and inspect a synthetic test batch first. Supply a JSON array such as `[["IMG.jpg", "beach.jpg"]]` in a separate requests file.
2. Run `python scripts/safe_photo_copy.py plan SOURCE_FOLDER OUTPUT_FOLDER requests.json` and capture its JSON output outside the photo folders as the review plan. Planning creates no photos. Review the complete final mapping and estimated disk needs, not only naming outliers. It reserves occupied names and numbered/case-only collisions; planned rows contain original SHA-256 hashes.
3. Only after approval, run `python scripts/safe_photo_copy.py copy reviewed-plan.json --approved`. The flag records an operator choice; it is not itself proof of user consent. Execution revalidates the whole plan, refuses changed sources/destinations, then exclusively creates each destination and compares both destination and retained-source hashes to the reviewed hash.
4. Read the returned JSON and exit status. Report only `copied_verified` rows as successful copies. `not_copied`, `incomplete_copy`, and `not_attempted` are not successful renames. On an error, later rows are not attempted. A partial output may remain; disclose its exact path and ask before cleanup. Do not retry blindly or overwrite that path. No automatic rollback or deletion occurs.
5. If in-place renaming is specifically required, the bundled helper is not that capability. Return the reviewed mapping and explain the limit, or use an independently verified no-overwrite rename implementation with the same containment, collision, retained-byte, and truthful-report guarantees. Do not substitute `rename()`/`replace()` where an existing destination can be overwritten.

The helper verifies byte identity, not image readability, EXIF correctness, attribution, or visual naming quality. Source timestamps/permissions and copied filesystem metadata are not promised. Prior prompt-supplied preservation tests passed; these reusable fixtures extend coverage, not document a historical overwrite failure.
